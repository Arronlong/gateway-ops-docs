# 渠道历史核对与回补

v1.1.1 起，渠道调用日志提供条数核对、异常区间定位与历史回补。它读取渠道自身凭据账号的上游使用记录，不是中转站管理员报表，也不是主动模型测试。手工余额渠道不提供这一操作；无凭据账号、连接器能力不足或上游不可读时，不能据空结果认定没有消费。

## 入口与操作

1. 打开渠道管理，选择需要对账的时间范围。v1.1.2 已取消进入页面、切换范围及每 30 秒页面刷新触发的自动条数核对。
2. 点击“重新拉取历史”，弹窗初始沿用页面范围；也可改选今天、24 小时、7 天、30 天、全部或自定义。
3. 点击“开始核对并补齐”，依次查看总体差异、异常区间与处理进度；仅打开弹窗不会自动执行回补。
4. 查看已保存页数 / 条数、账号错误和最终状态。条数一致但处理尚未完成时，不能仅凭绿色数字判定任务已完成。
5. 中断后使用“继续处理”；HTTP 429 等待恢复时，保持弹窗打开可自动继续。HTTP 403 应先检查权限或站点访问限制，不要靠重复点击绕过拒绝。

核对和回补会读取上游管理接口，不发送付费模型调用；仍会消耗上游查询额度并触发限流。时间范围与时区见 [指标口径](/logic/metrics)。

## 全渠道后台定时任务

在“系统设置 → 后台任务与同步”的“全渠道用量核对与修复”配置，默认启用、每天北京时间 07:00 执行最近 24 小时。修改开关、范围或时间后点击“保存任务设置”，保存后动态更新，无需重启；关闭定时开关不会删除历史，仍可手动立即执行。

| 范围 | 后台任务窗口 |
| --- | --- |
| 今天 `today` | 北京时间当天 00:00 至执行时刻。 |
| 24 小时 `24h` | 执行时刻向前滚动 24 小时，默认值。 |
| 7 天 `7d` | 执行时刻向前滚动 7 × 24 小时，与页面 7 个自然日预设有别。 |
| 全部 `all` | 不设起点，结束避开最近未稳定几分钟；受上游可查范围限制。 |

每日时刻固定按 `Asia/Shanghai` 调度，不跟随浏览器时区或服务器 `TZ` 改变。默认 07:00 的 24 小时窗口约为前一天 07:00 至当天 07:00，并非只核对前一天自然日，也不是每次全历史扫描。

“立即执行”使用数据库中已保存的范围，先保存草稿再执行；返回接受任务只表示已启动，结果在“执行记录”查看。支持关闭浏览器后继续，最长约 24 小时，同一全渠道任务运行中不重复启动。服务退出会取消本轮；已保存页和连续断点保留，后续运行继续处理，不承诺停机期间按日补跑。

任务依次读取全部渠道，包括暂停监控的自动余额渠道；手工余额渠道跳过并记录。某个渠道失败后继续下一渠道，记录总数、成功、失败与跳过；单个渠道内部账号失败仍可能中断该渠道剩余处理。它复用现有回补流程、单渠道互斥和上游请求预算，不调用付费模型，不替代渠道余额 / 倍率完整同步。

页面的单渠道入口继续保留，按弹窗范围处理。页面刷新只读业务视图，不再发自动校对请求；普通渠道同步中分轮推进历史的逻辑也继续保留。任务配置见 [系统设置](/guide/system-settings)，状态和日志见 [执行历史](/logic/task-execution-history)。

## 核对的到底是什么

```text
可比较的本地条数 = 所选窗口内本地条数 - 单独保留的更早历史条数
条数差异 = 可比较的本地条数 - 上游可核验条数
```

| 状态 | 含义与后续操作 |
| --- | --- |
| 条数一致 `matched` | 可比范围的数量一致；同时查看处理阶段是否完成。不是金额、Token 或每一条内容均一致的证明。 |
| 条数差异 `mismatch` | 已知可比条数不一致；看账号明细和异常时间段，再执行回补。 |
| 暂无法核对 `unavailable` | 总数不可靠、接口不可读或部分账号失败；保留原因，不显示成正常。 |
| 区间尚未稳定 `pending` | 有效稳定窗口尚未形成；稍后再查，不等于零调用。 |

上游日志有保留期。已经存到本地、但早于上游当前可查起点的记录，会单独计入保留历史，不用它们制造“本地多了”的差异。上游早已清理且本地从未保存的日志无法凭空恢复；“全部”只表示尝试读取可获得的历史，不承诺覆盖账号生命周期。

## 普通同步、每日核对与手动回补

自动用量同步不再只按“首次回填 30 天”理解。近期增量与历史连续核对各有独立进度：近期默认从最近成功同步位置向前重叠 10 分钟读取，起点不早于当前时刻前 24 小时；历史从保存断点继续，不能用近期最新一页跳过旧缺口。

自动历史处理每轮最多读取 3 页，保留未完成断点，后续同步继续；没有未完成任务时，完整历史检查约每 24 小时再安排一次。因此一次普通同步不代表已经回补全部历史。手动回补用于集中处理所选范围，逐页报告进度，不依赖刷新界面重复触发。

常规条数核对把结束点限制在“当前时刻减 2 分钟后向下对齐 5 分钟”，预设起点向上对齐 5 分钟；自定义起点保留。这样避免把仍在落库的最新调用立即判为缺失。核对实际返回的起止时间可能小于页面所选范围，最近几分钟尚未纳入核对不等于查询漏数。自动历史及“全部”回补也采用稳定截止点；其他手动范围以接口返回的实际窗口为准。

## 定位差异与逐页保存

- 普通条数核对先读总体；一致时跳过分段，不反复下载全部历史。
- 存在差异时按月 → 周 → 天缩小范围；这些内部定位边界按 UTC 划分，不等同于浏览器展示的自然日。已一致子区间跳过，异常区间才继续核对和补齐。
- 每页有效记录取得后立即入库，重叠读取按渠道、账号、来源及远端记录标识去重更新。只有分页完整且数量 / 边界校验通过，才确认区间完成并进行该区间必要的替换清理；不会先清空整个历史再重新下载。
- 连续完成位置、分页断点和近期同步位置分别保存到 PostgreSQL。请求取消、超时、分页重复 / 乱序或数量变化时保留收到的数据，不越过尚未确认的缺口；后续可能重新读取边界页，不保证每页只请求一次。

报告中的“修复前：本地多 N 条”保留的是处理前差异；右侧“已修复”表示对应区间已完成处理，不能把这行当作修复后的现存差异。完整核验的覆盖区间会清理上游本次未返回的多余记录，但早于上游可查边界的保留历史仍按原规则单列。Sub2API 全历史报告补充按账号区间的已核对 / 已修复 / 中断状态、页数和保存条数；总数未确定时显示计数待确认，不用初始零值判断一致。

报告中的“已保存条数”是本轮保存进度，可能包含更新已有记录，不等同于净新增条数。异常天数和修复天数也不是上游请求数量；每个账号的结果应分别核对。手动历史处理中某个账号失败可能提前中断后续账号，不能认为剩余账号已经处理完成。

## NewAPI 的数量上限与日志类型

NewAPI 的 `total=2000` 可能是接口截断，不作为可信总条数。历史扫描按月组织，遇到截断继续拆成周、天、小时；大月区间也会继续缩小。无法取得可靠分页或最小区间仍不能证明完整时，保留未完成状态，不以 2000 条直接宣布完成。

连接器区分消费与失败日志，校验上游是否执行类型和时间筛选；充值等非调用记录不混入调用计数。图片等调用可能没有普通文字 Token，不能仅因 Token 为零丢弃。NewAPI 历史映射与去重可能更新旧记录，修复数量需以最后重新核对结果为准，不能把计数相等解释为费用完全一致。

## 等待、限流与并发边界

| 约束 | 当前行为 |
| --- | --- |
| 同一渠道 | 用量同步 / 回补互斥；已有任务运行时不会再并行启动一份。 |
| 同一上游来源 | 按协议、主机和端口共享请求限制；不同渠道账号不会各自获得独立预算。 |
| 基础预算 | 请求至少间隔 2 秒，180 秒窗口内最多 60 次；达到预算显示等待，恢复后继续。 |
| HTTP 403 / 429 | 默认冷却 3 分钟；支持上游 `Retry-After`，429 后后续预算会进一步收紧。 |
| 流式进度 | 单次流式核对 / 手动回补最长 20 分钟，并发送保活；结束或断开不是清空数据。 |

“等待上游请求额度”表示尚未发送下一次查询，不是任务卡死。HTTP 403 检查凭据权限和防护规则；429 等到提示时间，不要多标签页反复启动。等待与失败都不应伪装为“条数一致”。

## 与其他数字的关系

回补完善的是渠道调用记录，可能影响区间调用数、用量和由这些记录计算的统计，但不直接调整手工余额，不生成充值账本，也不改变调组或优先级规则。余额采样消耗、渠道调用金额及中转站用户扣费仍是不同来源，见 [渠道余额与调用记录](/logic/channel-consumption)、[成本与倍率](/logic/cost-accounting) 和 [渠道与中转站调用对比](/logic/call-comparison)。
