# 通知与验证码规则

通知由采集或业务操作产生事件，经策略处理和订阅匹配后投递。验证码求解用于上游登录；两者配置、测试和失败原因各自独立。

## 订阅匹配

只有启用的通知渠道参与投递。非空订阅列表中任意一条规则命中即可：上游渠道 ID 必须相同，`all` 接受该渠道事件，`groups` 只在倍率变化事件上额外要求分组名命中。

选择特定分组不会阻断同渠道的余额不足、登录失败等其他事件。空订阅、`null`、空列表以及当前解析失败后的降级行为都视为订阅全部，不是“不接收任何事件”；希望停发时应关闭通知渠道。

事件包括余额不足、倍率变化、登录失败、验证码失败及监控失败。普通分组过滤使用分组名称精确匹配，不是按包含关系匹配。

## 倍率变化阈值与合并

```text
变化幅度百分比 = abs(新倍率 - 旧倍率) / abs(旧倍率) × 100
```

变化幅度达到最小阈值才推送；默认 `0` 表示不过滤。旧倍率为 `0` 时不执行除零，变化按达到阈值处理。过滤只影响通知，已经检测到的变化仍记录到倍率变化日志。

默认开启批量合并。一轮采集内，先筛掉幅度不足的变化，再为每个通知渠道筛出它订阅的分组，最后合并为该通知渠道的一条消息。关闭合并后按单条变化发送。

例如阈值为 5%，倍率 `1 → 1.04` 不推送，`1 → 1.05` 达到阈值；两条变化仍可留在变化日志中。

## 低余额冷却

默认同一上游渠道的 `balance_low` 事件在 60 分钟内不重复投递；设为 `0` 时每次符合条件的扫描都可通知。冷却状态持久化到 PostgreSQL，重启应用不会自动清除。

当前冷却占位发生在通知分发前，发送最终失败也可能已经占用冷却窗口。测试成功但下一轮没有余额通知时，还需检查阈值、订阅和冷却，不应只查看 Provider 是否可达。

## 失败重试与日志

默认最多尝试 3 次，包含第一次发送，所以最多追加 2 次重试。设为 `1` 不重试；非正配置在发送侧归一为至少 1 次。

退避间隔为 `1 / 2 / 4 / …` 秒，最高 30 秒；上下文取消会结束后续重试。重试发送同一事件，不重新执行余额采集或修改倍率。最终结果写通知日志。

“测试通知”走测试发送路径，不验证正常订阅、冷却及批量策略，也不能据此认定所有业务事件都会通知。

## Turnstile 流程

支持 CapSolver、2Captcha、Anti-Captcha 和 YesCaptcha。渠道需要开启 Turnstile 并绑定具体验证码配置：

```text
读取上游 site key → 用绑定 Provider 求解 → 将 token 带入登录 → 登录与会话保存
```

未开启或未绑定时不进入该准备流程；上游返回空 site key 时跳过求解。绑定配置已禁用、密钥无效、服务无余额或网络失败时返回错误，不自动依次尝试其他 Provider。

验证码测试和真实求解可能消耗服务额度。先确认 Provider 类型与凭据，再确认渠道的站点地址、Turnstile 开关和绑定关系。操作入口见 [通知与验证码](/guide/notifications)，启动策略参数见 [配置项](/reference/configuration)。
