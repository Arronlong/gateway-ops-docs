# 通知与验证码

通知渠道配置投递目标，验证码服务配置上游登录所需的 Turnstile 求解。先各自测试，再绑定到实际业务对象。

## 与预警中心的关系

v1.0.5 的 `/alerts` 统一展示预警事件、订阅规则、通知渠道与发送记录，旧 `/notifications` 入口继续可用。新规则的对象范围、阈值、动作及渠道选择见 [预警中心](/guide/alerts)。本页保留传统通知和验证码配置。

预警规则没有勾选通知渠道时只记录事件与动作；传统通知渠道的空订阅则表示全部，两者不要混淆。预警规则有独立冷却及恢复通知，不套用下表的传统低余额 60 分钟冷却。

## 配置通知渠道

支持 Telegram、Webhook、SMTP 邮件、企业微信、钉钉、飞书和 Bark。填写对应凭据与目标、启用渠道并执行测试；测试只验证测试投递路径，不验证全部业务订阅和冷却。

订阅可按上游渠道或分组设置。分组过滤只约束倍率变化，同上游其他事件仍可匹配；空订阅在当前实现中表示订阅全部，关闭通知渠道才是停发。

## 全局发送策略

| 策略 | 内置默认值 | 设置位置 |
| --- | --- | --- |
| 同轮倍率变化合并 | 开启。 | 后端启动配置。 |
| 最小变化幅度 | 0%，不过滤。 | 后端启动配置。 |
| 低余额冷却 | 60 分钟，同渠道跨重启有效。 | 后端启动配置。 |
| 最大发送尝试 | 3 次，含首次。 | 后端启动配置。 |

倍率阈值影响通知，不删除变化日志。发送失败也可能占用低余额冷却；测试成功却未收到告警时，需依次检查业务阈值、订阅、冷却和发送日志。

公式与特殊情况见 [通知与验证码规则](/logic/notifications-and-captcha)，环境变量与生效方式见 [配置项](/reference/configuration)。

## 配置 Turnstile

支持 CapSolver、2Captcha、Anti-Captcha、YesCaptcha。新增 Provider 后执行测试，再在使用密码登录的渠道账号上启用 Turnstile 并绑定该配置。Token 模式不走普通密码验证码登录。

系统只调用绑定 Provider；配置禁用或求解失败时，不自动轮换其他 Provider。测试和真实求解可能消耗额度。失败时核对密钥、余额、site key、页面地址、代理及渠道绑定。
